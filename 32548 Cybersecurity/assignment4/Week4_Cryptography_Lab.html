Intro

This week the lab is about the basic stuff that make secure communication works - so symmetric encryption first, then the asymmetric one (RSA), and also the whole X.509 certificate part which is what make HTTPS possible. There was 5 tasks in total and i done each one from the terminal by using OpenSSL, and for the last task i setup a small HTTPS server so i can actually see how the certificate trust is working in real. Below i put all the screenshots and also the exact commands that i used for every task.

Task 1 – Symmetric Encryption & Decryption

Symmetric encryption basically mean you use one single shared key for both locking and unlocking the data. For this one i used AES-128 with the CBC mode. The main thing that i noticed is that after encryption the file become totally unreadable, and to get the original back you need the exact same key and IV, if not it just wont work.

Q1 – Text file (Text_file.txt)

Commands i used for the encryption and also the decryption:

openssl enc -aes-128-cbc -e -in Text_file.txt -out text_cbc.enc -K 00112233445566778899aabbccddeeff -iv 0102030405060708090a0b0c0d0e0f10 openssl enc -aes-128-cbc -d -in text_cbc.enc -out text_dec.txt -K 00112233445566778899aabbccddeeff -iv 0102030405060708090a0b0c0d0e0f10
Fig 1. The original text, then the encrypt command, and cat text_cbc.enc showing the scrambled ciphertext - now you cant read the text anymore.

Q2 – Image file (image.bmp)

Same cipher but this time on the image file. Because the encrypted one is a binary i opened it with nano instead (if you open a binary with cat the terminal just get all messed up):

openssl enc -aes-128-cbc -e -in image.bmp -out image_cbc.enc -K 00112233445566778899aabbccddeeff -iv 0102030405060708090a0b0c0d0e0f10 openssl enc -aes-128-cbc -d -in image_cbc.enc -out image_dec.bmp -K 00112233445566778899aabbccddeeff -iv 0102030405060708090a0b0c0d0e0f10
Fig 2. The encrypted image inside nano, all the original bitmap bytes are completely scrambled.
Fig 3. The full round trip for both file - after decrypt, head text_dec.txt show the original text again, and file image_dec.bmp say "PC bitmap ... 1658 x 1611", so the decryption bring back the files exactly the same.

Observation: when you encrypt a file with some cipher/mode it give a totally different unreadable output, and you need the same key + IV to reverse it. Also the mode you pick is actually matter a lot in the real world - ECB mode leak the structure because the same plaintext block always turn into the same ciphertext block, but CBC (the one i used) chain the blocks together with a IV so no pattern is showing. This is basically the exact weakness behind the Adobe breach in 2013, they stored around 153 million password with 3DES in ECB mode and the researchers manage to recover the common ones without even breaking the key at all.

Task 2 – Asymmetric (RSA) Encryption

Asymmetric encryption is when there is a key pair - a public key that anyone can use for encrypt, and a private key which only the owner have for decrypt. So i made a file with my name inside, generate the key pair, and then encrypt using the public key and decrypt using the private one.

echo 'Jinkyung' > file.txt openssl genpkey -algorithm RSA -out private.pem -pkeyopt rsa_keygen_bits:2048 openssl rsa -pubout -in private.pem -out public.pem openssl rsautl -encrypt -inkey public.pem -pubin -in file.txt -out file.enc openssl rsautl -decrypt -inkey private.pem -in file.enc -out dec.txt
Fig 4. (1) file.txt with my name inside, and (2) the private key (private.pem) that got generated.
Fig 5. (3) the public key (public.pem), which is derived from the private key.
Fig 6. (4) encrypting with the public key, then cat file.enc show the scrambled ciphertext.
Fig 7. (5) decrypting with the private key - cat dec.txt give back my name, so only the private key can undo what the public key locked.

Observation: whatever you encrypt with the public key can only be open with the matching private key. Which mean the private key is like the most sensitive thing in the whole scheme - the Heartbleed bug (2014) is a good example here, it was a memory leak flaw in OpenSSL that let the attacker read the server private key straight out of the memory, so they could decrypt the traffic or pretend to be the server, doesnt matter how strong RSA itself is.

Task 3 – Becoming a Certificate Authority (CA)

In this task i make myself into a root CA. First i copy the OpenSSL config file, change its working directory to the current folder, and create the folder/file structure that the CA database is needing. After that i generate a self-signed root certificate.

cp /usr/lib/ssl/openssl.cnf ./ # edited openssl.cnf so that: dir = ./ mkdir crl certs newcerts touch index.txt echo '01' > serial openssl req -new -x509 -keyout ca.key -out ca.crt -config openssl.cnf
Fig 8. The dir in the config is now ./, and ls show the CA structure: certs, crl, index.txt, newcerts, openssl.cnf, serial.
Fig 9. Generating the self-signed CA cert. The details i put: AU / NSW / SYD / UTS / FEIT / cybersec.com.au / root@cybersec.com.au. After that ls show ca.key and ca.crt is created.

Observation: the root CA private key (ca.key) is very powerful - whoever have it can sign a "valid" certificate for basically any name. This is exactly what happen in the DigiNotar (2011) case, the attacker used the trusted CA own signing process to issue more than 500 fake certificates (one of them was even for *.google.com), and that is the reason why the real CAs are audited so heavily.

Task 4 – Issuing an X.509 Certificate for cybersec.com.au

Now i am acting as the CA and i issue a certificate to a "website". There is 3 steps for this one - generate the server key, make a Certificate Signing Request (CSR), and then let the CA sign it.

openssl genrsa -aes128 -out server.key 1024 openssl req -new -key server.key -out server.csr -config openssl.cnf openssl ca -in server.csr -out server.crt -cert ca.crt -keyfile ca.key -config openssl.cnf
Fig 10. Generating the server key and the CSR command with the details i entered (Organization = UTS, Common Name = cybersec.com.au). The challenge password and the optional company name i left them blank.
Fig 11. The CA signing the CSR - "Signature ok", the certificate details, then Sign? y / commit? y and "Data Base Updated". Now ls show the issued server.crt.

Observation: the openssl ca step is the exact legit signing operation that issue a trusted certificate - which is the same step the DigiNotar attackers abused from inside the compromised CA to issue certificates for domain they dont even own.

Task 5 – Using PKI for a Web Site (HTTPS)

For the last task i use the certificate to run a HTTPS server and see how the browser trust is actually working. I point the domain to localhost, put the key and the certificate together into one server.pem, and then launch the OpenSSL test web server.

echo "127.0.0.1 cybersec.com.au" | sudo tee -a /etc/hosts cp server.key server.pem cat server.crt >> server.pem openssl s_server -cert server.pem -www
Fig 12. Launching the HTTPS server with server.pem - it reach the ACCEPT state and listen on port 4433.

Before trusting the CA

When i first visit https://cybersec.com.au:4433 in Firefox it give me a warning, because the browser have no reason yet to trust my self-signed CA:

Fig 13. "Your connection is not secure - the owner of cybersec.com.au has configured their website improperly". This is the browser correctly refuse to trust an unknown CA.

Importing and trusting the CA

So i imported ca.crt into Firefox (Preferences → Advanced → Certificates → View Certificates → Authorities → Import) and tick "Trust this CA to identify websites".

Fig 14. The Certificate Manager (Authorities) is now showing UTS → cybersec.com.au, so my CA is trusted.

After trusting the CA

Fig 15. Reloading https://cybersec.com.au:4433 now load with a padlock and a valid TLS session (TLSv1.2, ECDHE-RSA-AES128-GCM-SHA256, "Verify return code: 0 (ok)").

Observation: before i import my CA, Firefox block the site with the untrusted certificate warning; after i add ca.crt as a trusted authority, the exact same site load with a padlock and no warning at all. This show the core idea of the web trust model - a browser will trust any certificate that is signed by a CA it already trust. But it also show the danger: the Lenovo Superfish (2015) case is exactly this checkbox but abused in a big scale, a self-signed root CA with a recoverable private key was pre-installed on the laptops so the adware could silently intercept all the HTTPS traffic without any warning showing to the user.

Reflection

Doing all the steps by hand make it clear to me that in all the four real incidents above, the actual maths of AES and RSA was never really broken - the failure was always in how the crypto get used, configured or trusted (a wrong cipher mode, a leaked private key, a compromised CA, or a certificate that is trusted without any good reason). So understanding why every command, flag and warning message exist is the thing that actually prevent these kind of mistake in a real deployment.
